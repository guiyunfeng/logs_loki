流程说明页

日志平台流程说明

本说明页重点描述日志从采集、存储、查询、转换到三个主面板展示的完整链路，以及日常排查时每个页面承担的职责。

高级分析 看整体风险、服务健康、异常检测、根因和预测洞察。
日志统计分析 看趋势、分布、Top N 错误以及多维筛选结果。
Grafana 面板 看实时监控、告警列表、日志流和服务聚合视图。

系统使用说明

当前系统首页提供 3 个主入口，建议排查顺序为：先看整体，再看分布，最后看实时状态。

首页入口

  1. 高级分析：先看风险范围和受影响服务。
  2. 日志统计分析：再看错误趋势、Top N 和筛选结果。
  3. Grafana 面板：最后看实时告警和日志流是否仍在持续。

时间范围

  1. 页面加载时根据默认时间窗口发起 Loki 查询。
  2. 切换时间范围后重新计算开始时间和结束时间。
  3. 前端按当前窗口重新聚合趋势、Top N 和服务维度数据。

数据降级

  1. Loki 查询成功时显示真实数据。
  2. 若 Loki 无数据或查询失败，则回退到 mock 数据。
  3. 保证页面在演示、验证和排查时不出现空白页。

1. 数据从哪来

当前代码中的数据主链路是“业务错误日志 → Promtail 标签化 → Loki 存储 → 前端 LogQL 查询 → 本地转换聚合 → 各分析面板展示”。

flowchart TD A[业务服务输出 error.log] --> B[Promtail 采集与打标签] B --> C[Loki 存储日志流] C --> D[前端发起 LogQL 查询] D --> E[前端标准化转换] E --> F1[高级分析页] E --> F2[日志统计分析页] E --> F3[Grafana 面板页] F1 --> G[服务健康 根因 异常 预测] F2 --> H[趋势 分布 TopN 筛选] F3 --> I[仪表盘 告警 日志流] I --> J[告警分级与通知展示] C -. 查询失败或无数据 .-> K[Mock 数据降级] K -. 保持页面可用 .-> F1 K -. 保持页面可用 .-> F2 K -. 保持页面可用 .-> F3

采集与存储

  1. 业务服务持续产出错误日志文件。
  2. Promtail 负责采集日志，并补充 job、level、project、app、error_type、filename 等标签。
  3. Loki 负责保存日志流，并支持按时间范围与标签进行检索。

前端查询与转换

  1. 前端通过 LogQL 查询指定时间范围内的日志流。
  2. 把纳秒时间戳转为可读时间，并尝试解析 JSON 日志正文。
  3. 若 project/app 缺失，则从 filename 中补全归属信息。
  4. 把 level 统一成大写，保证筛选和聚合逻辑一致。

2. 页面与面板对应关系

三个主页面复用同一批 Loki 原始数据，但每个页面的聚合方式和展示重点不同。

页面 核心目标 主要展示内容 适合回答的问题
高级分析 洞察整体风险 总日志量、错误率、服务健康、根因、异常、预测 系统当前稳不稳？风险在扩大还是回落？
日志统计分析 快速定位问题 趋势图、级别分布、项目服务拆分、Top N、筛选器 哪里报错最多？哪个项目和服务最值得优先排查？
Grafana 面板 实时监控与告警展示 指标卡、错误类型、趋势、告警列表、实时日志流、服务维度 错误是否还在持续？是否已经达到高等级告警？

3. 一次日常排查怎么使用这套系统

建议流程是“先看整体，再看重点，再看实时，最后回到业务系统修复并持续观察趋势”。

flowchart LR A[进入首页] --> B[高级分析] B --> C[确认错误率与受影响服务] C --> D[日志统计分析] D --> E[查看趋势 分布 TopN] E --> F[Grafana 面板] F --> G[确认实时告警与日志流] G --> H[返回业务系统修复] H --> I[再次观察趋势是否回落]

推荐动作顺序

  1. 先进入高级分析，判断问题是局部异常还是系统性异常。
  2. 再进入日志统计分析，锁定高发时段、高频错误和集中服务。
  3. 最后进入 Grafana 面板，看实时日志和告警是否还在持续发生。
  4. 根据结果返回业务系统、配置项或依赖服务进行修复。

排查产出

  1. 知道影响范围：几个项目、几个服务、哪些服务器。
  2. 知道主要问题：哪类错误最常见、哪条错误最频繁。
  3. 知道当前状态：是否仍在发生、告警是否升级。
  4. 知道修复效果：趋势是否回落，日志流是否恢复平稳。

4. 三个主页面关注点

高级分析

整体洞察
  • 汇总总日志量、总错误量、错误率和受影响服务数。
  • 根据服务错误比例计算 healthy、degraded、critical 状态。
  • 从错误模式中提取根因线索和异常波动点。
  • 输出性能画像和预测性风险提示。
服务健康 根因分析 异常检测 预测洞察

日志统计分析

快速定位
  • 支持按时间范围、级别、服务器、项目、服务和关键字过滤。
  • 展示错误时间趋势，识别异常峰值与高发时段。
  • 展示严重级别分布与项目服务拆分。
  • 展示 Top N 错误，帮助确定优先治理项。
趋势图 分布图 Top N 多维筛选

Grafana 面板

实时监控
  • 显示指标卡、错误类型分布和最近 24 小时趋势。
  • 把日志按项目和应用聚合成告警列表。
  • 展示最近日志流，用于判断异常是否仍在持续。
  • 展示服务或服务器维度的受影响情况。
指标卡 告警列表 实时日志流 服务聚合

5. 告警与处置闭环

当前代码中的告警更偏“前端可视化判断”，核心是按项目、应用或服务聚合错误，再映射为不同严重等级，辅助值班和处置。

flowchart LR A[错误日志持续出现] --> B[前端聚合统计] B --> C[判断频次与影响范围] C --> D[映射为 warning error critical] D --> E[告警列表展示] E --> F[研发或运维介入处理] F --> G[返回页面继续观察] G --> H{趋势是否回落} H -- 是 --> I[恢复日常监控] H -- 否 --> J[继续升级排查]

告警判断

  • warning：错误出现但影响范围有限。
  • error：错误频次上升，需要尽快介入。
  • critical：错误数量或影响面明显扩大，需要升级处理。

运维动作

  • 确认是单服务问题还是公共依赖问题。
  • 结合 Top N 错误和实时日志流快速定位异常来源。
  • 修复后持续观察趋势和告警列表是否回落。

系统价值

  • 把原始日志变成可读、可筛选、可汇报的监控结果。
  • 让“看日志”变成“看趋势、看影响面、看告警”。
  • 在 Loki 异常时依然保证页面有可演示和可验证数据。

6. 当前实现中的关键字段说明

字段 来源 用途 当前处理方式
job Promtail 标签 识别服务器或服务源 用于服务聚合和服务器筛选
level Promtail 标签 识别日志级别 统一转成大写后参与筛选
project / app 标签或 filename 识别项目与应用归属 优先取标签，缺失时从 filename 补全
error_type Promtail 标签 错误归类 做简化处理后用于分布和 Top N 统计
content / message / msg 日志正文 JSON 展示错误信息 按优先级解析，解析失败回退原文
