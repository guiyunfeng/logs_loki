日志平台流程说明

本说明页重点描述 error.log 单源采集、前端自动分级（CRITICAL/HIGH/MEDIUM/LOW）、紧凑双卡布局与告警建议逻辑，确保文档与页面实现一致。

高级分析 看整体风险、服务健康、异常检测、根因和预测洞察。
日志统计分析 看自动分级趋势、双分布紧凑卡、Top N 错误与筛选结果。
Grafana 面板 看实时监控、告警列表、日志流、服务聚合，以及内置 LogQL 查询。

系统使用说明

当前系统首页提供 3 个主入口，建议排查顺序为：先看整体，再看分布，最后看实时状态。

首页入口

  1. 高级分析：先看风险范围和受影响服务。
  2. 日志统计分析：再看错误趋势、Top N 和筛选结果。
  3. Grafana 面板：最后看实时告警、日志流，以及用 LogQL 做精准查询。

时间范围

  1. 页面加载时根据默认时间窗口发起 Loki 查询。
  2. 切换时间范围后重新计算开始时间和结束时间。
  3. 短窗口使用分钟区间（如 30m），避免 Loki 小数小时语法错误。
  4. 前端按当前窗口重新聚合趋势、Top N 和服务维度数据。

数据降级

  1. Loki 查询成功时显示真实数据。
  2. 若 Loki 无数据或查询失败，则回退到 mock 数据。
  3. 保证页面在演示、验证和排查时不出现空白页。

1. 数据从哪来

当前代码中的数据主链路是“业务 error.log → Promtail 标签化 → Loki 存储 → 前端 LogQL 查询 → 本地自动分级与聚合 → 各分析面板展示”。

flowchart TD A[业务服务输出 error.log] --> B[Promtail 采集与打标签] B --> C[Loki 存储日志流] C --> D[前端发起 LogQL 查询] D --> E[前端标准化转换] E --> X[自动分级引擎] X --> Y1[关键词命中 => CRITICAL] X --> Y2[按频次 => HIGH MEDIUM LOW] Y1 --> F1[高级分析页] Y2 --> F1 Y1 --> F2[日志统计分析页] Y2 --> F2 E --> F3[Grafana 面板页] F2 --> H[等级趋势 双分布 TopN 筛选] C -. 查询失败或无数据 .-> K[Mock 数据降级] K -. 保持页面可用 .-> F1 K -. 保持页面可用 .-> F2 K -. 保持页面可用 .-> F3

采集与存储

  1. 业务服务持续产出 error.log（当前源日志只有 error 级别）。
  2. Promtail 负责采集日志，并补充 job、project、app、filename 等标签。
  3. Loki 负责保存日志流，并支持按时间范围与标签进行检索。

前端查询与转换

  1. 前端通过 LogQL 查询指定时间范围内的日志流。
  2. 把纳秒时间戳转为可读时间，并尝试解析 JSON 日志正文。
  3. 若 project/app 缺失，则从 filename 中补全归属信息。
  4. 执行自动分级：命中致命关键词标 CRITICAL，否则按频次划分 HIGH/MEDIUM/LOW。

2. 页面与面板对应关系

三个主页面复用同一批 Loki 原始数据，但每个页面的聚合方式和展示重点不同。

页面 核心目标 主要展示内容 适合回答的问题
高级分析 洞察整体风险 总日志量、错误率、服务健康、根因、异常、预测 系统当前稳不稳？风险在扩大还是回落？
日志统计分析 快速定位问题 自动分级趋势、紧凑双分布卡、项目服务拆分、Top N、筛选器 当前主导风险等级是什么？哪个项目和服务最值得优先排查？
Grafana 面板 实时监控与告警展示 指标卡、错误类型、趋势、告警列表、实时日志流、服务维度、LogQL 查询器 错误是否还在持续？是否达到高等级告警？某条日志能否用 LogQL 精准复现？

3. 一次日常排查怎么使用这套系统

建议流程是“先看整体，再看重点，再看实时，最后回到业务系统修复并持续观察趋势”。

flowchart LR A[进入首页] --> B[高级分析] B --> C[确认错误率与受影响服务] C --> D[日志统计分析] D --> E[查看自动分级趋势 双分布 TopN] E --> F[Grafana 面板] F --> G[确认实时告警与日志流] G --> H[返回业务系统修复] H --> I[再次观察趋势是否回落]

推荐动作顺序

  1. 先进入高级分析，判断问题是局部异常还是系统性异常。
  2. 再进入日志统计分析，锁定高发时段、高频错误和集中服务。
  3. 最后进入 Grafana 面板，看实时日志和告警是否还在持续发生。
  4. 根据结果返回业务系统、配置项或依赖服务进行修复。

排查产出

  1. 知道影响范围：几个项目、几个服务、哪些服务器。
  2. 知道主要问题：哪类错误最常见、哪条错误最频繁。
  3. 知道当前状态：是否仍在发生、告警是否升级。
  4. 知道修复效果：趋势是否回落，日志流是否恢复平稳。

4. 三个主页面关注点

高级分析

整体洞察
  • 汇总总日志量、总错误量、错误率和受影响服务数。
  • 根据服务错误比例计算 healthy、degraded、critical 状态。
  • 从错误模式中提取根因线索和异常波动点。
  • 输出性能画像和预测性风险提示。
服务健康 根因分析 异常检测 预测洞察

日志统计分析

快速定位
  • 支持按时间范围、自动等级、服务器、项目、服务和关键字过滤。
  • 展示自动分级趋势，识别异常峰值与高发时段。
  • 右侧为“等级分布 + 服务器分布”紧凑双卡。
  • 展示 Top N 错误，帮助确定优先治理项。
趋势图 紧凑双卡 Top N 多维筛选

Grafana 面板

实时监控
  • 显示指标卡、错误类型分布和最近 24 小时趋势。
  • 把日志按项目和应用聚合成告警列表。
  • 展示最近日志流，用于判断异常是否仍在持续。
  • 展示服务或服务器维度的受影响情况。
  • 内置 LogQL 查询器，支持快速试验 query、限定时间窗并验证过滤效果。
指标卡 告警列表 实时日志流 服务聚合 LogQL 查询

7. Grafana 面板中的 LogQL 查询功能

当前系统在 Grafana 面板页内集成了 LogQL 查询模块，可用于补充可视化卡片之外的精确检索与验证。

适用场景

  • 想验证某个项目/服务是否在特定时间窗内持续报错。
  • 想用标签组合（如 job、project、app）快速缩小范围。
  • 想对 Top 错误中的关键字做二次确认，判断是否仍在发生。
  • 想在告警前先手工验证 query 的命中准确性。

建议使用步骤

  1. 先在日志统计分析页锁定目标项目/服务与时间段。
  2. 进入 Grafana 面板的 LogQL 查询区，拼装基础查询。
  3. 逐步追加过滤条件（标签或关键字段）并缩小时间窗。
  4. 确认命中结果后再回到告警与处置流程执行升级动作。

5. 告警与处置闭环

当前告警判断基于“自动分级 + 频次阈值 + 影响面”，并在页面中给出 P1/P2/观察建议，用于值班决策与处置升级。

flowchart LR A[错误日志持续出现] --> B[前端聚合统计] B --> C[关键词判定 CRITICAL] B --> D[同类错误频次分级] C --> E[生成 CRITICAL HIGH MEDIUM LOW] D --> E E --> F[页面给出 P1 P2 观察建议] F --> G[研发或运维介入处理] G --> H[返回页面继续观察] H --> I{趋势是否回落} I -- 是 --> J[恢复日常监控] I -- 否 --> K[继续升级排查]

告警判断

  • CRITICAL：命中致命关键词（如 OOM、磁盘满、连接池耗尽）。
  • HIGH / MEDIUM / LOW：按同类错误在窗口内出现次数自动分级。
  • 建议：CRITICAL 存在则优先 P1，HIGH 累积过高则 P2，否则观察。

运维动作

  • 确认是单服务问题还是公共依赖问题。
  • 结合 Top N 错误和实时日志流快速定位异常来源。
  • 修复后持续观察趋势和告警列表是否回落。

系统价值

  • 把原始日志变成可读、可筛选、可汇报的监控结果。
  • 让“看日志”变成“看趋势、看影响面、看告警”。
  • 在 Loki 异常时依然保证页面有可演示和可验证数据。

6. 当前实现中的关键字段说明

字段 来源 用途 当前处理方式
job Promtail 标签 识别服务器或服务源 用于服务聚合和服务器筛选
level Promtail 标签 原始日志级别 当前源日志仅 error，不作为最终等级依据
project / app 标签或 filename 识别项目与应用归属 优先取标签，缺失时从 filename 补全
error_type Promtail 标签 错误归类 做简化处理后用于分布和 Top N 统计
content / message / msg 日志正文 JSON 展示错误信息 按优先级解析，解析失败回退原文
severity(自动) 前端推断字段 告警判断与趋势分线 关键词优先 CRITICAL，其余按频次归为 HIGH/MEDIUM/LOW
